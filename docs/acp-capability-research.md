# Command Code ACP capability research

Inspected locally on 2026-10-31 against installed Command Code 1.88.2 and T3 Code Beta 0.1.5. This list covers gaps identified by this investigation, not every tool or command. Command Code's ACP documentation says the harness keeps its tools and skills; tool execution and rendering a terminal-only UI are different capabilities.

Update 2026-11-04: bridge 2.0 adds native plan-mode commands, reconstructed markdown plan display, explicit approval, and plan-feedback continuation. Full editor parity and exact plan identity across concurrent native planning sessions remain limited by missing native ACP metadata. See [current bridge investigation](./bridge-reliability.md). The table below records the earlier investigation.

| Capability | Current behavior | Possible future work |
|---|---|---|
| Terminal `/context` analysis | Terminal runs `analyzeCommandContext` over the active harness messages and collects tool, MCP, skill, agent and memory information. ACP emits a separate `usage_update`; the mod API exposes `getContextUsage`, but not this analysis. The bridge's `/context` cannot claim parity. | Command Code could expose the existing analysis as a structured ACP command or documented mod API and send it to T3. Test identical session state, model settings and before/after compaction, including breakdown. Copying private bundled functions would be version-sensitive and still needs access to the live session state. |
| Native `/compact` presentation and outcome | ACP `/compact` invokes native session compaction. Terminal formats its own notice; ACP formats a different notice. Both can report no change; outcome detail can be lost. The mod's `/com` uses the same native compaction and observes outcome events. | Expose the same structured compaction outcome and UI notice through ACP; test summarized, too-small, failure and cancellation. Exact output and post-compaction token analysis require upstream support. |
| Multi-select and custom answers | Command Code maps each question to a permission request and accepts one option ID. Neither multiple choices nor arbitrary text can round-trip. The bridge shows a single-choice form and cancels unrecognized text. | Add structured question and answer transport to Command Code ACP, with capability negotiation and T3 mapping. Tests must cover actual responses, cancellation, grouping and full access. |
| Option descriptions and grouped questions | Command Code emits separate permission requests for each question; the current T3 generic enum form repeats labels rather than rendering separate descriptions. | Extend structured transport to preserve question IDs, descriptions and grouping; T3 must render those fields and return the corresponding IDs. |
| Plan review | Prior local inspection showed native review behavior depends on permission mode and that the ACP question path drops plan-specific payload fields. The existing mod has a partial plan gate; cancellation and parallel execution remain caveats. | Expose the complete plan content and review metadata in ACP, render a native plan review in T3, and test mode changes, cancellation and parallel actions. Recheck against current versions before patching. |
| Terminal-only statusline UI | Installed ACP explicitly labels `/statusline` terminal-only. | Provide a T3-native status configuration or structured equivalent. A proxy alone cannot render the terminal overlay. |

References: https://commandcode.ai/docs/acp , https://commandcode.ai/docs/context , https://commandcode.ai/docs/mods . The installed Command Code bundle and existing T3 source were inspected; behaviors can change between versions. No unsupported capabilities were implemented as part of this research.
